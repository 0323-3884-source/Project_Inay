# Project INAY database backup and recovery

## Access and scope

Only explicitly approved administrator accounts can generate, download, validate and restore full-system database-record backups: `admin` (ID 1, role admin), `admindswd` (ID 2, role admin_dswd), and `admincho` (ID 3, role admin_cho). Exact ID/username/role entries are maintained in `config/backups.php`; new administrators do not inherit access. Unknown accounts, missing grants, retired roles and changed identities fail closed. This permission is limited to backup/recovery; ordinary departmental routes retain their existing restrictions. Backup/recovery requests use the authenticated admin session, CSRF protection and rate limiting. Password re-entry was removed at the user's request.

An authorized deployment operator must review changes to this grant list, rebuild Laravel's configuration cache during the normal deployment process and restart long-lived workers where applicable. Grants are application configuration, not restored database records. Railway account identities must match the approved entries; mismatches deny access rather than granting role-wide fallback. Account renaming, deletion/recreation or role changes require a new approval review. No self-service grant form or database migration was added.

The Backup and Recovery sidebar link opens /admin/backups. New SQL files are stored under the private local disk's database-backups directory and are also downloadable. Recent backups include pre-restore safety copies. They are not placed in public storage.

The archive includes application database records for mothers, infants, maternal monitoring, growth, vaccination, appointments, clinical messages/calls, casefile assignments, learning data, F1KD/4Ps compliance, evaluations, notifications and all account tables, including password hashes. It excludes live sessions, cache/locks, queued jobs, reset tokens and migration history. This is a data-only SQL backup: it requires an already-installed matching schema and does not contain CREATE TABLE/database definitions, application code, environment secrets or uploaded storage files. Keep the versioned code/migrations, application key and the public/private upload volumes in a separate controlled disaster-recovery plan.

## Safe recovery flow

1. Generate a current backup and keep an encrypted off-site copy. Local private files alone do not protect against a lost deployment volume.
2. Choose an unmodified SQL backup generated by this installation. The app validates its HMAC, format, database driver and schema before staging it privately. Your existing admin login authorizes the action; no password re-entry is needed.
3. Review the backup timestamp, driver and table count. Validation does not write to the application records. The preview is bound to the current administrator session and expires after 15 minutes.
4. Inform users and pause queue workers, schedulers and external database writers. The web guard blocks ordinary application requests during the recovery, but it does not stop workers or already-running transactions. Use an operator-controlled maintenance window on production, particularly across replicas.
5. Type RESTORE ALL DATA and confirm that background writers are paused. The app acquires an operation lock and must save a fresh private safety copy before touching records.
6. All included tables are replaced transactionally. Foreign-key relationships are checked before commit; an execution failure rolls back database changes. An absent usable administrator role also rejects recovery.
7. Active database sessions are cleared and the session epoch is rotated. Sign in afterward using administrator credentials from the recovered backup. Current account/password/role changes made after the backup are replaced too.

Only installation-generated signed SQL is accepted by the web interface; arbitrary SQL and modified files are rejected. The signature uses the existing APP_KEY, which is not included in the file. If the key or schema changed, use a controlled operator recovery procedure rather than bypassing signature/schema validation. The signature authenticates the SQL; it does not encrypt the archive. The downloaded SQL contains confidential information and must be protected.

Recovery requires database-backed sessions outside automated tests so pre-recovery sessions can be removed durably. Use a shared database/Redis cache for operation locks and session-epoch consistency across replicas, and a shared persistent private volume for backups. Do not use the array cache in production. The application refuses nontransactional MySQL table engines. Do not run schema migrations concurrently with backup/recovery.

## Compatibility and limits

- Implemented drivers: MySQL/MariaDB with InnoDB tables and SQLite. PostgreSQL and SQL Server fail closed with an unsupported-driver message; use provider-native backups for those engines.
- SQL files restore database records only. Missing photos, medical documents and attachments cannot be recovered from SQL; restore the corresponding storage-volume snapshot separately.
- Web archives are limited to 20 MiB. Larger databases should use provider/native backup tools. Inserts are batched in groups of 100 rows to reduce remote database round trips.
- Docker includes an INI file allowing a 20 MiB upload, a 24 MiB request, 256 MiB memory and 180 seconds execution. These settings have not been built or exercised on Railway. The host/reverse proxy may impose lower limits.
- Private safety copies are retained, not automatically deleted. Configure a reviewed retention policy, off-site encrypted copies and disk-space monitoring. Expired staging files are removed when their owning session revisits the page or replaces its preview; orphan staging files require operator cleanup.
- New requests are blocked during recovery for up to the operation lease (five minutes). Worker pause, replica coordination and point-in-time recovery remain operational responsibilities.
- SQL can also be inspected/imported by an authorized operator, but manual imports bypass web recovery safeguards. They require a maintenance window, matching schema, verified integrity, independent rollback copy, session invalidation and storage consistency checks.

## Implementation files

- app/Support/DatabaseBackup.php: consistent data export, signed SQL framing, schema validation, transactional recovery and foreign-key verification.
- app/Http/Controllers/Admin/BackupController.php: admin authorization, private files, preview, operation lock, safety copy, recovery and sanitized audit events.
- app/Http/Middleware/DatabaseRecoveryGuard.php: temporary request blocking and post-recovery session invalidation.
- config/backups.php: excluded operational tables and archive size cap.
- app/Models/AdminUser.php, app/Providers/AppServiceProvider.php, config/backups.php, routes/web.php, resources/views/layouts/admin.blade.php: explicit account approval, backup Gate, backend route restrictions and conditional existing navigation.
- resources/views/admin/backups.blade.php: backup, validation, confirmation and private-download controls using existing admin styling.
- AuthController, AdminAuthController and bootstrap/app.php: session-epoch initialization and middleware registration.
- Dockerfile and docker/backup-limits.ini: deployment upload/runtime settings.

No migration, production deployment, password reset or actual database recovery was executed during implementation.

## Technical references

MySQL requires transactional tables for consistent transactional backups: [MySQL Backup and Recovery](https://downloads.mysql.com/docs/mysql-backup-excerpt-8.0-en.a4.pdf). SQLite supports deferring foreign-key enforcement until transaction completion: [SQLite PRAGMA documentation](https://sqlite.org/pragma.html#pragma_defer_foreign_keys). These informed the export/recovery transaction and relationship checks; they are not evidence that Railway restore drills have been performed.
